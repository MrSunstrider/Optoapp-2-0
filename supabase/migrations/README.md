# Migrations — Supabase Schema Management

> **Golden Rule**: Every schema change MUST go through migration files. **Never use the Supabase
> Dashboard** to edit tables, columns, policies, or functions in production or staging. The
> Dashboard is read-only for schema inspection. If you used the Dashboard to make a change, that
> change will be overwritten on the next `supabase db push` and the diff will fail CI.

---

## The Golden Path

This is the **only** approved workflow for making schema changes:

```mermaid
flowchart LR
    A[supabase migration new] --> B[Write SQL]
    B --> C[supabase db lint]
    C --> D[supabase db reset]
    D --> E[supabase db diff --linked]
    E --> F[git add + commit]
```

### Step-by-step

```bash
# 1. Start the local Supabase stack (if not already running)
supabase start

# 2. Create a new migration file
#    Generates: supabase/migrations/YYYYMMDDHHmmSS_description.sql
supabase migration new add_foo_table

# 3. Write your SQL in the new file
#    - Use CREATE TABLE IF NOT EXISTS / ALTER TABLE / CREATE OR REPLACE FUNCTION
#    - Always add RLS policies with optica_id for multi-tenant isolation
#    - Always include updated_at triggers for audit columns

# 4. Lint the migration
supabase db lint

# 5. Apply all migrations + seed data in a clean environment
supabase db reset

# 6. Verify the local schema matches the remote project (zero drift expected)
supabase db diff --linked

# 7. Commit and push
git add supabase/migrations/20260712000001_add_foo_table.sql
git commit -m "feat: add foo table"
git push
```

> If `supabase db diff --linked` shows any diff, you introduced a schema change **outside**
> a migration file. Stop. Revert the Dashboard change, then create a proper migration.

## Migration File Rules

### Naming Convention

Format: `YYYYMMDDHHmmSS_description.sql`

- **Timestamp**: 14-digit UTC timestamp (generated by `supabase migration new`).
- **Separator**: Single underscore `_` between timestamp and description.
- **Description**: `snake_case`, brief but descriptive. Use existing files as a guide.

✅ Correct: `20260712000001_add_pacientes_table.sql`  
✅ Correct: `20260712000142_fix_rls_policy_for_inventario.sql`  
❌ Wrong: `my_migration.sql` (no timestamp)  
❌ Wrong: `2026-07-12-add-foo.sql` (wrong date format)  
❌ Wrong: `20260712000001-AddFooTable.sql` (not snake_case)

### Immutability

- **Never** modify, rewrite, or delete a migration file after it has been committed.
- **Never** reorder or rename migration files (the timestamp prefix is the sort order).
- To undo a change, create a **new** migration that reverses it.

### Structure

- Wrap DDL changes in `IF NOT EXISTS` / `IF EXISTS` guards for idempotency.
- Add RLS policies in the same migration that creates the table.
- Use `COMMENT ON TABLE` / `COMMENT ON COLUMN` for documentation.
- Keep each migration focused on a single concern (one table, one function change, etc.).

## Migration Lifecycle

```
supabase migration new        → creates timestamped file
        │
        ▼
Write SQL + lint              → supabase db lint (syntax + naming check)
        │
        ▼
Apply locally                 → supabase db reset (reapplies all + seed)
        │
        ▼
Verify against remote         → supabase db diff --linked (zero drift expected)
        │
        ▼
Commit to git                 → push triggers CI validation
```

### CI Pipeline

On every push/PR touching `supabase/migrations/`, CI runs:

1. `supabase start` — boots local Postgres
2. `supabase db lint` — naming + SQL syntax check
3. `supabase db reset` — applies all migrations + seed data
4. Schema integrity tests — validates tables, columns, RLS, and functions
5. `supabase db diff --linked` — catches drift against the linked project

If any step fails, the pipeline **blocks the push**.

## Dashboard Prohibition

| Action | Allowed? | Alternative |
|--------|----------|-------------|
| View table data | ✅ Read-only | Supabase Studio Table Editor |
| View RLS policies | ✅ Read-only | `SELECT * FROM pg_policies;` |
| Add/modify columns | ❌ Never | `supabase migration new` + SQL |
| Create/alter functions | ❌ Never | `supabase migration new` + SQL |
| Add RLS policies | ❌ Never | SQL in migration file |
| Change project settings | ✅ Dashboard | Auth, API, Storage settings |

**Why**: Dashboard edits bypass the migration file workflow. They create a diff that
`supabase db diff --linked` detects as drift. Downstream consequences:

- CI pipelines fail with unexplained diffs
- Other developers' local environments diverge from production
- Rollback becomes impossible (no migration file to revert)
- The `supabase db push` deployment will overwrite Dashboard changes

## Deployment (to Production)

**`supabase db push` is the only approved deployment path.**

```bash
# 1. Ensure the linked project is correct
supabase link --project-ref your-project-ref

# 2. Deploy all pending migrations
supabase db push

# 3. Verify zero drift
supabase db diff --linked
```

`db push` applies migrations in order, one at a time, wrapping each in a transaction.
If a migration fails mid-way, the transaction rolls back and the process stops.

## Troubleshooting

### `supabase db lint` fails with "naming violation"

**Cause**: Migration filename doesn't match the `YYYYMMDDHHmmSS_description.sql` pattern.  
**Fix**: Rename the file to match the convention. Re-run `supabase db lint`.

### `supabase db reset` fails during migration

**Cause**: A migration file contains SQL that references objects that don't exist yet
(e.g., a table was renamed but another migration references the old name).  
**Fix**: Check the migration order. Ensure `IF NOT EXISTS` guards are used. Run
`supabase migration repair` if a migration was partially applied.

### `supabase db diff --linked` shows unexpected diff

**Cause** (most common): Someone edited the schema via the Supabase Dashboard.  
**Fix**:
1. Identify what changed: `supabase db diff --linked` shows the delta.
2. Create a migration file that captures the diff:
   ```bash
   supabase db diff --linked -f capture_dashboard_change
   ```
3. Review the generated file, adjust if needed, commit it.
4. **Stop using the Dashboard for schema changes.**

**Cause** (less common): A migration was committed without running `db diff --linked`.  
**Fix**: Run `supabase db diff --linked` against the linked project, commit any diff as a new migration.

### `supabase start` fails to boot

**Cause**: Port conflict or stale Docker state.  
**Fix**: `supabase stop --no-backup-volume` then `supabase start`.

### CI fails with "missing SUPABASE_ACCESS_TOKEN"

**Cause**: The GitHub secret `SUPABASE_ACCESS_TOKEN` is not set.  
**Fix**: Go to repo Settings → Secrets and variables → Actions → Add `SUPABASE_ACCESS_TOKEN`.

## Local Setup

### Activate Git Hooks

```bash
# Register the pre-commit hook for migration lint
git config core.hooksPath .githooks

# Verify it's active
git config core.hooksPath
# → .githooks
```

The pre-commit hook automatically runs `supabase db lint` whenever you stage files
in `supabase/migrations/`. It exits gracefully if the Supabase CLI is not installed.

### Seed Data

`supabase/seed.sql` populates the database with representative test data after reset.
It contains synthetic data (test domains, demo names) and is safe to run multiple times
(ON CONFLICT DO NOTHING). The seed runs automatically during `supabase db reset`.
