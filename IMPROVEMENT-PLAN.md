# Improvement Plan — OptoApp SaaS

## Summary

Found **38 findings** across security, architecture, code quality, performance, and DevOps. The codebase has strong fundamentals (SSR auth, RLS, Zod validation, clean architecture patterns) but has several systemic issues: a security-critical SQL injection vector in the PacienteRepository, rate-limiting that vanishes on cold starts, extensive logic duplication between web `lib/` modules and the domain layer, race conditions in financial write operations, an unused domain abstraction layer, and missing CI/CD. The recent test-coverage push covered roles, cierre-caja, rate-limit, reportes-financieros, inventario, and EvaluacionBuilder well — those are marked done.

## Priority Legend

- 🔴 CRITICAL — Bug, security, or data integrity risk
- 🟡 HIGH — Significant quality, performance, or maintainability concern
- 🔵 MEDIUM — Improvement that adds value but not urgent
- ⚪ LOW — Nice-to-have / cosmetic / future consideration

| # | Area | File(s) | Issue | Impact | Suggested Fix |

| C1 | Security | `web/src/data/repositories/SupabasePacienteRepository.ts:17` | **SQL injection via string interpolation in `.or()` filter**: `query.or(\`nombre_completo.ilike.%${s}%,...\`)` interpolates raw user input into a Supabase PostgREST filter string. A search like `%,id.neq.null` could manipulate the filter to leak data from other ópticas. | An attacker can craft a search string to bypass RLS-filtered queries and read data they shouldn't. | Use the same `escapeIlikeFragment()` pattern already in `pacientes.ts` — or better, use Supabase's `.or()` with parameterized values. | C2 | Security | `web/src/lib/rate-limit.ts` | **In-memory rate limiter resets on every serverless cold start**. Next.js on Vercel/similar spins down containers; the `Map` is empty after a cold boot, allowing unlimited PIN brute force. | The entire PIN brute-force protection is ineffective in production serverless. | Replace with a persistent store: either Supabase DB table (`pin_attempts` with expiration), Upstash Redis, or Vercel KV. At minimum, add per-IP + per-userId tracking with TTL in a DB table if keeping it simple. |
| C3 | Security | `app/src/main/.../SecurityManager.kt:23` | **Hardcoded default PIN `"123456"`**. EncryptedSharedPreferences protects at rest, but if the user never changes their PIN, it remains the trivial `123456`. On shared devices this is a real risk. | Any user who hasn't changed their PIN has `123456`. Combined with no rate-limit on Android, complete access is trivial. | Force a PIN change on first launch (one-time migration flag in DataStore). Remove the default or set it to a random value that forces initial setup. |
| C4 | Data Integrity | `web/src/app/pacientes/_actions/dispensacion-crud.ts:133-162`, `servicio-crud.ts:113-158` | **Race conditions in stock + payment writes**. The dispensación save performs a read → check → update on `monturas.stock_actual` and `pagos` without any transaction. Two concurrent saves can corrupt stock counts or create duplicate payments. | Under concurrent edits (two users or two tabs), stock can go negative or payments duplicated. The DB has CHECK constraints but the read-check-update window allows races. | Move stock adjustment to a Supabase RPC function that runs atomically (`UPDATE monturas SET stock_actual = stock_actual - 1 WHERE id = $1 AND stock_actual >= 1 RETURNING stock_actual`). For payments, wrap in a DB transaction or use the `WITH` CTE pattern in an RPC. |
